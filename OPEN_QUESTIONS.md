## 1. Stack — blocking, decide first

**1.1 Language boundary.** Slide 6 states slice A is "served via FastAPI" (Python).
I plan to define all cross-slice payloads as **Zod schemas** with generated DTOs
(TypeScript). Those two do not coexist for free. Which one:

- **Option A — Python everywhere.** FastAPI + Pydantic for all three slices. No Zod.
  Contract = OpenAPI generated by FastAPI.
- **Option B — split (my recommendation).** Slice A stays Python/FastAPI for the
  model. Slice B + C and the web app are TypeScript. One shared `packages/contracts`
  holding Zod schemas as the single source of truth; Python side validates against
  JSON Schema exported from those same Zod schemas. Every boundary parsed, never cast.
- **Option C — TypeScript everywhere.** Model training stays offline in notebooks,
  serving is TS. Cheapest to integrate, weakest ML story.

Ask: which one, and is Option B's shared contracts package acceptable as the
"written down" artifact slide 10 requires?

**1.2 Repo shape.** One monorepo (pnpm workspaces, three apps + shared contracts) or
three separate repos? Monorepo is the only shape where a frozen contract is
mechanically enforceable — a contract change breaks all three CI jobs immediately.
Three repos means the freeze is honour-system.

**1.3 Database.** Postgres assumed. Confirm — and confirm who provisions/pays.
Multi-year daily index across N regions is small, but slice B's queries are
time-series shaped.

**1.4 Hosting.** Deploy is due **end of Week 2**. Which platform, whose account,
who pays? Options we can afford: Railway, Fly.io, Render, Vercel (web only).
Blocking for Giyos as Release Owner.

**1.5 Scheduler.** The 07:00 KST job (slice C, mine): platform cron, GitHub Actions
schedule, or an in-app scheduler? This changes how I prove idempotency at M2.

## 2. Data — blocking, nothing starts without it

**2.1 data.go.kr API key.** Slide 16 calls this blocking with a "named owner."
Who is the named owner, and is the application submitted? If it is not submitted,
the whole build slips from day one.

**2.2 Exact endpoint(s).** Which specific data.go.kr service? Please send the
service name/ID, not just "the pollen index." KMA publishes several related feeds.

**2.3 Historical backfill.** Slices A and B both need **5+ years**. Does the API
serve history, or is history a separate bulk download / CSV? If bulk — where from,
and who does the one-time load?

**2.4 Region granularity + canonical list.** Slide 15 says "KMA region granularity
only." I need the **exact region codes and names**, frozen, as a shared enum in the
contracts package. Every slice keys off this: forecasts, charts, Telegram channels.
If this list changes in Week 3, all three slices break.

**2.5 Weather observations.** Slice A needs weather as model input. Separate API,
separate key? Same account?

**2.6 Rate limits and quota.** Requests/day on the key. Determines whether we cache
into our own DB (my assumption: yes, we ingest nightly and never call KMA at
request time) or proxy live.

**2.7 Risk-level encoding.** The four levels — Low / Moderate / High / Very high.
What does the raw API return: integer 1–4, Korean strings, or a float index we
bucket ourselves? If we bucket, the thresholds must come from KMA, not from us.
